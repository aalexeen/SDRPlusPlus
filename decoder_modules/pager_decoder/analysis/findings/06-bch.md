# Stage 06 — BCH(31,21) Error Correction

## Summary verdict

**BCH is NOT faithfully ported — one real correctness bug, matching the reported symptom.** The core GF(2^5) math, primitive polynomial, bit ordering, and single-/double-error correction of the C++ `BCHCode::decode` are algorithmically sound and equivalent to the C reference. **However, the C++ decode path completely omits the even-parity (bit 31) miscorrection gate that the C ground truth `bch_flex_next_correct` performs.** The C reference operates on the full 32-bit FLEX word: after applying a BCH correction it checks even parity over bits 0–30 plus the received bit 31, and *rejects* the word (`-1`) when the total error count is odd (i.e. 3+ real errors that happen to alias to a valid 1- or 2-bit syndrome). The C++ port strips bit 31 at intake (`received[]` is built only from bits 30..0, and `data & 0x7FFFFFFF` is masked in), so those miscorrections are silently accepted and written back as "corrected" — producing valid-looking-but-wrong words across a phase. This is the #1 cause of "messages displayed but incorrect." A secondary, currently-harmless issue: the C++ return-value semantics are collapsed (0 = any success, 1 = uncorrectable; never -1 or a 2-bit count), but no C++ call site depends on the lost information, so it is informational only.

### Notes on the two decoder algorithms (context, not a defect)

The C reference (`bch.c`) is a **table-driven** corrector: it precomputes a `(S1<<5)|S3 → error-pattern` lookup (`flex_err_tbl`) plus the even-parity gate. The C++ `BCHCode` is the classic **Morelos-Zaragoza on-the-fly** corrector: it forms syndromes s[1..4], detects single vs double error via `s3 == 3*s1`, builds a degree-2 error-locator, and runs a Chien search. Both are valid BCH(31,21,t=2) decoders and produce the same 1-/2-bit corrections for ≤2 real errors. They diverge only for 3+-error inputs, where the C reference's parity gate (BCH-01) rejects and the C++ port miscorrects. This divergence is exactly the reported symptom and is the single most important fix.
